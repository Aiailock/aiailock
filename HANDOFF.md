# HANDOFF: проект «Для тебя» — цифровой дневник из WhatsApp

Этот файл — точка входа для продолжения проекта в **новом чате** (в том числе
с другого аккаунта). Вставь его целиком первым сообщением, приложи текущий
zip-архив проекта (`whatsapp-timeline-stage*.zip`) — и Claude сможет
продолжить ровно с того места, где остановились, не теряя контекст и не
переспрашивая то, что уже решено.

---

## 1. Что это за проект (полное ТЗ от заказчика)

Production-ready сайт с базой данных на Supabase и деплоем фронтенда на
Netlify. Это цифровая книга / личный дневник / архив переписки / фотоальбом /
временная линия отношений, который превращает экспорт переписки WhatsApp в
красивую интерактивную историю для одного конкретного человека.

**Ключевой принцип:** никакого прямого подключения к WhatsApp (не Bridge, не
Web, не QR, не webhook/API, не постоянные процессы). Только обычный
ZIP-экспорт чата, который заказчик периодически выгружает из WhatsApp и
загружает в закрытую админку.

**Формат экспорта:** внутри ZIP — текстовый файл (`chat.txt` или похожее имя)
в формате `ДД.ММ.ГГГГ, ЧЧ:ММ - Имя: сообщение`, плюс медиафайлы по конвенции
WhatsApp (`IMG-`/`PTT-`/`AUD-`/`STK-`/`VID-` + дата + номер + расширение).
Парсер должен быть устойчив к вариациям формата (разные локали Android/iPhone),
не жёстко привязан к одному примеру.

**Что должен делать импорт ZIP:**
- Распаковать, найти текстовый файл, определить формат.
- Распарсить сообщения, включая многострочные (одно сообщение может занимать
  несколько строк).
- Определить дату/время/отправителя каждого сообщения.
- Отличить обычные сообщения от системных (шифрование, «сообщение удалено»,
  добавление в группу и т.п.) — системные не показывать читателю.
- Сопоставить упоминания медиафайлов с реальными файлами в архиве.
- Сохранить всё в БД в хронологическом порядке.
- Не дублировать уже импортированные сообщения при повторной загрузке.

**Дедупликация:** fingerprint = устойчивый хеш от связки
(дата + время + отправитель + текст + имя медиафайла), не порядковый номер.
Повторная загрузка того же архива → «новых сообщений не найдено», ничего не
дублируется. Если медиафайл не найден в архиве — импорт не должен падать,
сообщению присваивается статус «медиа не найдено».

**Сценарий использования:** при первом импорте заказчик вручную выбирает
дату начала истории (всё раньше — не импортируется). При всех следующих
загрузках система сама помнит, докуда дошла история в прошлый раз
(`history_settings.last_imported_at`), и дозаписывает только новое —
без повторной настройки. Пример: 1-й импорт — с 1 января по 20 августа;
через неделю заказчик грузит уже весь чат целиком (1 января – 27 августа) —
система сама находит, что добавить нужно только 21–27 августа.

**Отчётность по импорту:** сколько сообщений всего/новых/дублей, сколько
фото/видео/аудио, есть ли отсутствующие медиа — плюс история всех импортов
(дата, имя файла, сколько добавлено, статус, ошибки) и пошаговый лог процесса
(найден файл → распарсено N → сопоставлены медиа → найдены дубли → сохранено
→ обработано ИИ). Одна плохая запись не должна ронять весь импорт.

**Читатель (`/`, публичная страница):**
- Ни единого намёка на техническую часть: ни admin, ни импорт, ни база, ни
  ИИ, ни ошибки парсинга, ни внутренние id.
- Одна длинная непрерывная страница сверху вниз, без меню и навигации.
- Новый импорт → новая часть истории сама появляется в конце.
- Ощущение личного дневника / цифровой книги, не дашборда, не мессенджера,
  не соцсети, не блога.

**Админка (`/admin`, закрытая):**
- Загрузка ZIP, статистика, история импортов и логи.
- Управление ИИ, включая ручной перезапуск обработки (отдельных сообщений
  или всех) — старые обработанные сообщения сами по себе не переписываются
  без команды.
- Ручное добавление фото/скриншотов/воспоминаний: дата, место в истории
  (после сообщения/даты), подпись, стиль, анимация.
- Редактирование элементов истории и настроек оформления.
- **Preview as reader** — страница ровно такой, какой её увидит читатель, без
  единого админского элемента, включая мобильный превью ~390×844.

**Стили оформления фото/скриншотов** (должны чередоваться, не повторяться):
рамка телефона, floating (наклонённый), polaroid, карточка-воспоминание,
фрагмент разговора из нескольких изображений, тонкая розовая линия, цветы по
углам, сердечки по краям, веточки/листья, «старая бумага»/письмо, золотая
тонкая рамка, звёзды, ленты. Видео — архитектурно с самого начала (плеер,
превью-кадр, ленивая загрузка, без загрузки тяжёлых файлов целиком). Аудио —
минималистичный плеер с длительностью. Реакции — место под них
предусмотреть архитектурно, но их отсутствие ничего не ломает.

**Текст:** сообщения никогда не выглядят как в мессенджере (не «[Я] 22:13:
текст», а «23 августа 2025, 02:17 — короткая красивая фраза»). В базе всегда
раздельно `original_text` (реальный текст из экспорта) и `display_text`
(обработанная версия) + кнопка «оригинал» у читателя. ИИ: чинит ошибки и
пунктуацию, слегка улучшает читаемость, определяет настроение (`mood`:
normal/romantic/sad/funny/deep/night/memory/important/hopeful/neutral) и
**предлагает** (не жёстко навязывает) фон/рамку/декор/анимацию — админ
принимает или меняет. ИИ никогда не сочиняет и не добавляет то, чего не было
в оригинале. Если ИИ недоступен — `display_text = original_text` с базовым
стилем, ничего не ломается. Результаты кэшируются (модель + версия промпта),
чтобы не гонять повторно без необходимости.

**Визуал:** путешествие по цвету/настроению по мере скролла — кремовый →
розовый → белый с розовым → персиковый → лавандовый → тёмно-фиолетовый
(ночь) → бордовый (пик эмоций) → снова светлый. Плавные scroll-based
переходы (Framer Motion / CSS), без резких скачков. Настоящие SVG-иллюстрации
(цветы, розы, веточки, листья, лепестки), не только эмодзи. Лепестки — редко
и мягко. Сердечки — редкие, аккуратные. Лёгкий параллакс, без укачивания.
Scroll-reveal — fade + лёгкое смещение, без bounce/резкого scale. После
сильных эмоциональных моментов — намеренная пауза (пустое пространство).
Переход между годами — отдельная визуальная пауза с новым цветовым этапом.
Иногда — «в этот день год назад». Финал — не footer, а ощущение конца книги
с пониманием, что новый импорт продолжит историю.

**Технически:**
- Универсальная модель `timeline_elements` — единая хронология из разных
  типов контента (сообщение/фото/видео/аудио/скриншот/воспоминание/
  переход года/«в этот день»), чтобы добавлять новые типы без переписывания
  архитектуры.
- Supabase: Postgres + Storage + Auth + RLS, раздельные таблицы (не одна
  большая), медиа в Storage с логическим разделением по типу.
- История может содержать десятки тысяч сообщений → пагинация/виртуализация
  на бэкенде, но визуально для читателя — ощущение одной бесконечной
  страницы без заметных подгрузок.
- Читатель не имеет доступа к админке — обеспечено Auth + RLS + noindex/
  security headers; ссылка открывается без регистрации/пароля/QR, если
  заказчик сам не включит защиту.
- PWA (manifest, иконки, offline-friendly оболочка), но установка не
  обязательна.
- Фронтенд: React, TypeScript, Vite, Tailwind, Framer Motion, Lucide React.
  Тяжёлая логика (парсинг ZIP, сопоставление медиа, дедупликация, ИИ) — на
  бэкенде, не во фронтенде.
- Доступность: контраст, alt, `prefers-reduced-motion`, семантичный HTML,
  клавиатурная навигация в админке. Тест на 320/360/375/390/414/430/768/
  1024/1440px, основной фокус — 390×844.

**Процесс разработки (по этапам заказчика):**
1. Архитектура и фундамент (структура, Supabase-схема, Storage, Auth, RLS,
   типы, базовый бэкенд/фронтенд, README).
2. ZIP-импорт и парсер чата (многострочные, системные сообщения, дубли,
   логи импорта).
3. Медиа-движок (фото/видео/аудио/скриншоты, сопоставление, отсутствующие
   медиа, миниатюры).
4. ИИ и timeline-движок (original/display текст, настроение, стиль, кэш,
   ручная переобработка, сборка единой хронологии).
5. Визуальная часть для читателя (цветовые переходы, рамки, декор, ритм,
   mobile-first).
6. Полноценная админка (импорт, история, логи, управление контентом,
   настройки, ИИ-контроль, preview как читатель + мобильный preview).
7. Интеграционное тестирование, адаптив, безопасность, производительность,
   доступность, обработка ошибок → единое production-ready состояние.

**Правила разработки:** на каждом следующем этапе не переписывать готовые
части с нуля — проверять совместимость, чинить баги, добавлять новое поверх
существующего, следить что сборка не ломается. Ничего не симулировать: если
что-то заявлено готовым — оно должно реально работать; если пока нельзя
реализовать полностью — прямо сказать и оставить архитектуру на будущее.
README подробно объясняет архитектуру, установку, Supabase, ИИ, деплой,
форматы экспорта, медиа, дедупликацию, troubleshooting — и отдельно понятно
для заказчика: как получить ZIP-экспорт из WhatsApp и загрузить его на сайт.

**Стилевая основа:** визуальный референс — файл `reader-prototype.html`
(шрифты Cormorant Garamond, DM Sans, Caveat, пиксельные VT323/Press Start 2P
для админки; палитра кремовый/розовый/персиковый/лавандовый/бордовый/
золотой; плавающие лепестки; scroll-reveal). Дизайн-токены уже перенесены
в `tailwind.config.ts` проекта.

**Пример реального экспорта:** заказчик прикладывал реальный ZIP
(`Чат WhatsApp с контактом Х.txt` + медиафайлы по конвенции WhatsApp) —
использовался только для проверки структуры архива (имена файлов, формат),
**содержимое переписки не читалось и не должно читаться** — заказчик просил
ориентироваться на формат, не на личное содержание.

## 2. Архитектурные решения, которые уже приняты (не пересматривать без причины)

- Единая таблица `timeline_elements` как читательская лента поверх отдельных
  источников (`messages`, `media`, `memories`, `screenshots`) — так новые
  типы контента не требуют переписывания рендера.
- RLS — реальная граница безопасности, а не только проверка на клиенте:
  `is_admin()` в Postgres проверяет `auth.uid()` против единственного
  `owner_user_id` в `app_config`.
- `history_settings` содержит чувствительные поля (`reader_password_hash`) —
  анону доступен **не** сам объект, а узкий `view` (`public_settings`).
- Storage — 7 приватных бакетов, никаких публичных URL; читатель получает
  медиа только через подписанные ссылки (реализация — этап 3).
- Fingerprint для дедупликации = хеш(sender + iso_timestamp + original_text +
  media_filename), не порядковый номер и не просто дата+время.
- `service_role` ключ Supabase — только в секретах Edge Functions, никогда
  в `VITE_`-переменных/фронтенде.
- Единственный owner-аккаунт (не система ролей) — проще и достаточно для
  одного администратора.

## 3. Текущий статус

- ✅ **Этап 1 (Архитектура и фундамент) — готов и проверен.**
  Полная Supabase-схема с RLS (`supabase/migrations/0001_init.sql`,
  `0002_auth_owner.sql`, `0003_storage.sql`), Storage-бакеты, Auth,
  фронтенд-скелет (Vite+React+TS+Tailwind с токенами из прототипа),
  роутинг `/` и `/admin`, рабочий вход в админку, `netlify.toml`, PWA,
  подробный README. Проект реально собирается с нуля: `npm install` →
  `npm run build` — без ошибок (проверено).
- ✅ **Этап 2 (парсер ZIP + дедупликация) — готов.**
  Парсер (`server/parser/`): оба формата заголовка (Android/iOS), любой
  разделитель даты, 12-/24-часовое время, многострочные сообщения,
  системные сообщения, старый и новый формат медиа-ссылок, «медиа
  отсутствует». Дедупликация по fingerprint (не по номеру) — устойчива к
  повторному и пересекающемуся импорту. Edge Function `import-zip`
  (приём → распаковка → парсинг → фильтр по дате начала → дедуп →
  сохранение → отчёт), рабочая форма загрузки в `/admin`.
  **Что реально проверено:** `server/parser/selfTest.ts` — 20/20 проверок
  на реалистичных примерах (Android/RU, iOS/EN, многострочность, дубли при
  обычном и при пересекающемся повторном импорте, битый заголовок),
  прогоняется через `npx tsx server/parser/selfTest.ts` без внешних
  зависимостей.
  **Что НЕ проверено в этой сессии (честно, не скрыто):** в песочнице, где
  делался этот этап, не было сети, поэтому нельзя было ни `npm install`
  (для сборки фронтенда — форма импорта не запускалась вживую), ни `deno`
  (для реального запуска/деплоя Edge Function). Код Edge Function
  (`supabase/functions/import-zip/index.ts`) проверен вручную построчно и
  по типам, использует только `npm:@supabase/supabase-js@2` и
  `npm:fflate@0.8.2` (стандартные npm-специфайеры Deno, дополнительно
  ставить ничего не нужно) — но перед тем как полагаться на неё в
  реальном использовании, обязательно прогони настоящий импорт на тестовом
  ZIP и проверь отчёт (см. README → «Как проверить, что парсер реально
  работает»). Если что-то не срастётся при первом реальном запуске — это
  ожидаемо первое, что стоит проверить в новом чате.
- ✅ **Этап 3 (медиа-движок) — готов.**
  В этой сессии сеть/npm БЫЛИ доступны (в отличие от Этапа 2): реально
  выполнены `npm install` и `npm run build` — оба без ошибок — и оба
  self-test (`server/parser/selfTest.ts` 20/20, новый
  `server/media/selfTest.ts` 9/9). Deno по-прежнему недоступен в песочнице,
  поэтому сама Edge Function не задеплоена/не вызвана вживую — см. пометку
  ниже.
  Что сделано:
  - `import-zip` теперь реально загружает байты совпавших медиафайлов в
    Storage (не только создаёт строку `media` со статусом `pending`, как
    раньше) — бакет выбирается по виду медиа (`server/media/paths.ts` →
    `bucketForKind`), путь детерминирован и включает `media.id` (без
    коллизий при повторной загрузке того же имени файла), `upsert: true`
    делает повторный импорт идемпотентным на уровне файлов, не только
    сообщений.
  - Настоящие миниатюры для фото в jpg/jpeg/png через `imagescript`
    (`npm:imagescript@1.3.0`, чистый WASM, без нативных зависимостей —
    та же логика выбора библиотеки, что и у `fflate` для ZIP): реальные
    `width`/`height`, ресайз до 480px по ширине, jpeg-миниатюра в бакет
    `thumbnails`.
  - Честно НЕ сделано (не скрыто, см. `MEDIA_ENGINE_NOTES` в начале
    `supabase/functions/import-zip/index.ts` и README → Этап 3): миниатюры/
    превью-кадр для видео, а также для webp/heic-фото и стикеров — нужен
    полноценный видео/универсальный image-декодер, не то, что разумно
    делать чистым JS/WASM в edge-функции за один проход. Сами файлы всё
    равно загружаются и доступны, просто без `thumbnail_path`.
  - Новая приватная Edge Function `get-media-url` — единственный способ
    получить рабочую (короткоживущую, 5 минут) подписанную ссылку на
    файл; авторизация — интерим-правило до Этапа 4 (проверяет, что медиа
    привязано к сообщению в пределах `reader_starts_at`), заменится на
    проверку через `timeline_elements` один-в-один, без ослабления, когда
    та таблица появится — подробности в комментарии в начале файла
    функции.
  - Новый бакет `documents` (`0004_media_documents_bucket.sql`) — раньше
    единственный вид медиа (`document`) не имел своего бакета.
  **Что реально проверено:** `npm install`, `npm run build` (оба чисто),
  `server/parser/selfTest.ts` (20/20, не сломано изменениями), новый
  `server/media/selfTest.ts` (9/9: сопоставление вид→бакет, санитизация
  имён файлов, детерминированные пути, MIME по расширению, и настоящий
  round-trip через `fflate` — собрать ZIP в памяти → распаковать → сверить
  байты по имени файла).
  **Что НЕ проверено в этой сессии (честно, не скрыто):** реальная загрузка
  в Supabase Storage, вызов `imagescript` под настоящим Deno-рантаймом,
  работа `get-media-url` против живой БД — в этой песочнице по-прежнему нет
  `deno`, только Node (npm-домены были доступны, deno.land/сам бинарник
  Deno — нет). Код обеих функций проверен вручную построчно и по типам.
  Перед тем как полагаться на медиа-движок в реальном использовании,
  обязательно прогони настоящий импорт с фото/видео/аудио и проверь, что
